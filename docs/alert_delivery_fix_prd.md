## 一、背景与问题

### 1. 现状：告警「落库了，但没送到人手里」
| 断点 | 位置 | 事实 |
| :--- | :--- | :--- |
| **webhook 为空** | `alerts.py:60` | `ALERT_WEBHOOK_URL` 未配置 → webhook 路径直接失败 |
| **白名单外 ERROR 被提前 return** | **`alerts.py:67-68`** | `not opened and not whitelisted → return` —— **事故已 OPEN 且不在白名单 → 连告警行都不写** |
| **飞书只推白名单或 CRITICAL** | `alerts.py:94-96` | 飞书群推送块，**白名单外 ERROR 默认不推群** |

> **白名单已扩充**：`FEISHU_GROUP_ALERT_WHITELIST` **现为 18 项**（10-23 夜已扩充），`OPTION_LIFECYCLE_RISK` / `DAILY_LOSS_KILL_SWITCH` / `REAL_TRADE_REJECTED` / `ORDER_ENV_MISMATCH` / `HARD_STOP_LIMIT_INVALID` **已在其中**。

### 2. 实测后果（未投递清单）

**今日（10-24）实况**：**25 条告警全部 `delivered=0`**，其中 **ERROR 13 条**，**全部是不在白名单的新事件**：

| 事件 | 级别 | `delivered` | 次数 | 意味着什么 |
| :--- | :--- | :--- | :--- | :--- |
| `PORTFOLIO_STRESS_BREACH` | ERROR | **0** | 10 | **组合压力突破，一次都没推** |
| `STRATEGY_ERROR` | ERROR | **0** | 2 | 策略异常，没推 |
| `VOLATILITY_SCANNER_ERROR` | ERROR | **0** | 1 | 雷达异常，没推 |
| 其余 12 条 | INFO | 0 | 12 | 恢复类通知（非紧急） |

**历史（10-23 夜之前，白名单扩充前）**——**属历史数据，不代表当前仍漏推**：

| 事件 | 级别 | `delivered` | 次数 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| `OPTION_LIFECYCLE_RISK` | ERROR | 0 | 42 | **扩充前历史**，现**已在白名单** |
| `DAILY_LOSS_KILL_SWITCH` | ERROR | 0 | 5 | 同上 |
| `REAL_TRADE_REJECTED` | ERROR | 0 | 3 | 同上 |
| `ORDER_ENV_MISMATCH` | ERROR | 0 | 2 | 同上 |
| `HARD_STOP_LIMIT_INVALID` | ERROR | 0 | — | 同上 |

> ⚠️ **口径纪律**：**必须区分「扩充前历史」与「当前实况」**——否则会把**已白名单化**的事件误报成「仍在漏推」。**本次修复要解决的是「当前实况」这 13 条 ERROR。**

**当前实况**：今日 25 条告警**全部未投递**（ERROR 13 条见上表）；未投递量**仍在累积**。历史累计只作背景，**不用于判断"当前仍漏推"**。

### 3. 为什么这是 P0
**告警系统的唯一价值是「让人知道」**。**落库不推送 = 没有告警**——用户只能靠翻日志或事后复盘发现，而**真金风险往往在发生那一刻就需要人介入**。

**用户明确要求过**：「对账拦截必须强告警」。**现在正是它没做到。**

## 二、用户与场景

| 用户 | 场景 | 核心诉求 |
| :--- | :--- | :--- |
| **交易员/用户** | 收到一条告警 | **知道是什么、多严重、该做什么** |
| **交易员/用户** | 没收到告警 | **知道是「没事」还是「推送坏了」**——**不能靠猜** |
| **交易员/用户** | 告警太多 | **能静音不重要的**，但**重要的不能被静音** |
| **运维/审计** | 事后复盘 | 能查**每条告警的投递状态**（送达/失败/失败原因） |

## 三、推送策略：默认推 ERROR 及以上，静音清单显式

### 1. 核心原则（方向反转）
**现状（错）**：默认静默，只有显式列入白名单的事件才推。
**改为（对）**：**默认推送 ERROR 及以上**；**防疲劳靠显式静音清单**（mute-list），**不靠默认静默**。

**理由**：**默认静默会吃掉真金信号**——今天 20 条未投递就是代价。

### 2. 必须推送的（不可协商）
| 级别/类别 | 处置 |
| :--- | :--- |
| **所有 ERROR 及以上** | ✅ **必须推送** |
| **涉及真金敞口/资金/风控门禁的事件（不论级别）** | ✅ **必须推送** |

### 3. 硬编码「不可静音清单」（配置覆盖不了）
```
DAILY_LOSS_KILL_SWITCH          单日亏损急停
REAL_TRADE_REJECTED             实盘报单被拒
ORDER_ENV_MISMATCH              执行环境不匹配
LEDGER_MISMATCH                 三账对账不一致
RISK_REJECTED                   风控拒绝
OPTION_LIFECYCLE_RISK          期权交割/行权风险
HARD_STOP_LIMIT_INVALID         止损限额配置无效
KILL_SWITCH_ENGAGED             急停触发
OPEND_DISCONNECTED              OpenD 掉线
RECONCILIATION_*                对账暂停/恢复
```
**理由**：这些是**真金安全信号**，静音它们等于**把安全系统变哑**。

### 4. 静音清单（可配，但受约束）
| 约束 | 说明 |
| :--- | :--- |
| **显式** | 必须逐个键入，**禁止通配**（不允许前缀/正则一次静默一类） |
| **可审计** | 每条要写清**谁批的、为什么、何时复审** |
| **不可静音清单优先** | 硬编码清单**永远覆盖**静音清单 |
| **静音有代价** | 被静音的事件**仍必须落库**，只是不推送 |

## 四、页面可见（告警必须「看得到」）

### 1. 告警中心页（新增或扩展）
| 区块 | 内容 |
| :--- | :--- |
| **今日告警摘要** | 总数 / ERROR 数 / **未投递数**（🔴 高亮） |
| **告警列表** | 时间、级别、事件、消息、**投递状态**（✅ 已送达 / ❌ 失败 + 原因） |
| **投递失败专区** | **未投递的告警单独列出**——**这是本次修复的核心可见性** |
| **静音清单** | 当前被静音的事件 + 批准人 + 原因 + 复审时间 |

### 2. 投递状态必须是**三态**（不是布尔）
| 状态 | 取值 | 含义 | 处置 |
| :--- | :--- | :--- | :--- |
| **未尝试** | `-1` | **根本没推**（通道未配置 / 被静音） | 检查通道配置 |
| **尝试失败** | `0` | **推了但失败**（webhook 挂了 / 飞书拒绝） | **重试**；持续失败 → 升级 |
| **成功** | `1` | 已送达 | — |

**为什么必须区分「未尝试」和「尝试失败」**：**「没推」是配置问题，「推失败」是故障**——混成一个 `0`，就分不出**「通道空着」和「通道坏了」**，而**这两者的处置完全不同**。

**落点**：`webhook_delivered` / `feishu_delivered` / `muted` **三个独立列**（不合并成一个布尔）。

### 3. 投递失败必须可见（关键）
**未投递的告警不能只躺在库里**——页面必须有**独立的「未投递」视图**：

```sql
severity IN ('ERROR','CRITICAL') AND delivered = 0 AND muted = 0
```

**按时间倒序。**

**🔴 必须带 `AND muted=0`**（采纳 Chief 意见）：**静音是人工明确的决策**——**被静音的事件不该混进「未投递」**，否则静音一多，「未投递」就被训练成噪声，**真正漏推的反而看不见**。

**理由**：**今天的缺口本质是「以为配了、其实没推」**。**只有「未投递」可见，才能在下次发生时立刻发现。**

### 4. 探针的递归防护（重要）
每 30 分钟对不可静音清单做一次**端到端投递验证**，失败发 CRITICAL `ALERT_DELIVERY_FAILED`。

**但探针自己也不投递时怎么办？** —— **由页面「未投递」视图兜底**。
**理由**：**不靠告警去发现告警故障**，那是**无限递归**（告警发不出去 → 发一条「告警发不出去」→ 这条也发不出去 → …）。**兜底必须是「人能看到的地方」，不是「另一条告警」。**

## 五、状态语义

| 状态 | 判据 | 展示 | 动作 |
| :--- | :--- | :--- | :--- |
| ✅ **已送达** | webhook/飞书返回成功 | 正常展示 | — |
| ❌ **投递失败** | webhook 失败 / 飞书失败 | **红色「投递失败」+ 原因** | **重试**；持续失败 → **升级** |
| 🔇 **已静音** | 在静音清单内 | 「已静音」标记 + 批准人 | 仍落库 |
| ⚠️ **某通道未配置** | 该通道的配置项为空（webhook 或飞书**分别判断**） | **按通道分别醒目警告** | **必须让人知道**；**另一通道可用时告警仍能送达** |
| 🛑 **通道全部未配置** | webhook 与飞书**都不可用** | **红色「告警通道全部未配置」** | **必须让人知道**；此时才是「只落库、不推送」 |

**关键**：**通道未配置本身必须可见**——今天的缺口就是**因为通道空着而没人知道**。

## 六、文案规范

| 场景 | 文案 |
| :--- | :--- |
| 投递失败 | `❌ 告警投递失败 · <事件> · 原因：<原因> · 将重试` |
| 单通道未配置 | `⚠️ <通道名>未配置 · 当前经另一通道推送`（**按通道分别显示**） |
| 通道全部未配置 | `🛑 告警通道全部未配置（webhook 与飞书均不可用）· 所有告警只落库、不会推送` |
| 未投递摘要 | `🔴 今日有 N 条告警未投递 · 请检查通道配置` |
| 已静音 | `🔇 已静音 · 批准人：<who> · 原因：<reason> · 复审：<date>` |

**禁止**：只写「投递失败」而不写原因；只写「已静音」而不写批准人。

## 七、空态与异常态

| 情形 | 展示 |
| :--- | :--- |
| 无告警 | 「所选条件下无告警记录」 |
| 全部投递失败 | 🔴 「**所有告警投递失败**」+ 通道配置指引 |
| 通道未配置 | ⚠️ 同上（**这是常态风险，不是一次性异常**） |
| 页面加载失败 | 「告警列表暂不可用」+ 重试，**不显示堆栈** |

## 八、验收（8 条，可演示）

1. **ERROR 必推**：构造一条 ERROR 告警 → **必须推送**（不再被白名单拦截）。
2. **不可静音清单生效**：把 `LEDGER_MISMATCH` 加入静音清单 → **仍必须推送**（硬编码清单覆盖静音）。
3. **静音清单生效**：把一个非关键 INFO 事件静音 → **不推送，但仍落库**。
4. **通配禁止**：静音清单填 `RISK_*` → **拒绝**，提示「禁止通配，请逐个列出」。
5. **未投递可见 + 静音不进未投递**：构造一次投递失败 → **「未投递」视图出现该条** + 显示失败原因；**另把一个 ERROR 事件静音 → 该条不出现在「未投递」视图**（`muted=0` 过滤生效），**但仍在告警列表里可见**。
6. **通道未配置可见（按通道）**：只清空 `ALERT_WEBHOOK_URL`（飞书可用）→ 页面显示 **webhook 通道警告**，**且告警仍经飞书送达**；再把飞书也断开 → 页面显示 **红色「通道全部未配置」** + `ALERT_CHANNEL_NOT_CONFIGURED`。
7. **三态可区分**：构造「通道未配置」（未尝试）与「webhook 返回失败」（尝试失败）→ **页面显示两种不同状态**，**不合并**。
8. **递归防护**：两个通道都断开 → 探针投递值为 **`-1`（未尝试）**、`ALERT_CHANNEL_NOT_CONFIGURED` 也发不出去，但**页面「未投递」视图仍显示该探针记录**（`delivered=0` 且 `muted=0`）——**不靠告警发现告警故障**。

**附加**：**投递验证探针**——定期（如每 30 分钟）对不可静音清单做一次端到端投递验证，**失败即告警**（「以为配了、其实没推」的根治）。

## 九、非目标（本期不做）
- 不做告警分级自动化（按内容判断级别）；
- 不做告警聚合/合并（同事件短时间多条）；
- 不做告警确认/关闭工作流（本期只做「可见 + 可送达」）。
