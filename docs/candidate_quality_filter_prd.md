## 一、背景与问题

### 1. 现象：今日 0 单，但不是「没信号」
| 数据 | 值 |
| :--- | :--- |
| `volatility_scanner` | 884 条 HOLD |
| `volatility_long_gamma` | 721 条 HOLD + **344 条 BLOCKED** |
| `order_intents` | **0** |

**BLOCKED 构成**：
- **279 次「期权行情已过期」**——快照延迟 1116–1759 秒，超 900 秒阈值；
- **65 次「合约已于 2026-10-23 到期」**——**雷达在选 T-0（当日到期）合约**；
- 当日 `OPTION_MARKET_DATA_BLOCKED` 279 条、`OPTION_QUOTE_DEGRADED_ACCEPTED` 597 条。

### 2. 根因（Ops 实测确认，根因①）
两个被挡合约**已订阅、在链上、OpenD 报价正常**，但**报价自 10-23 12:20 / 12:52 起冻结**，三次读数（间隔 10 秒）完全不变；**同期正股每秒刷新**。

**判定：低流动性期权报价本身稀疏，30+ 分钟无更新是常态——不是订阅故障。**

### 3. 定性
**门禁在正常工作，不是故障。真正的问题是：雷达把「不该交易的合约」选进了候选池。**

**所以方向是「候选质量」，不是「放宽门禁」。**

## 二、用户与场景

| 用户 | 场景 | 核心诉求 |
| :--- | :--- | :--- |
| **交易员/用户** | 发现今天没单 | 知道**为什么没单**——是「没机会」还是「被选品挡了」 |
| **交易员/用户** | 复盘候选 | 能看到**候选池里有什么、谁被排除、为什么** |
| **策略运维** | 调整选品松紧 | 能配过滤阈值，**且知道配了之后候选会少多少** |
| **复盘/审计** | 追溯 | 能查**每个被排除候选的原因** |

## 三、产品目标
**让「不该交易的合约」在候选池阶段就被摘除**，而不是走到数据质量门禁才被 BLOCK——**后者制造「没单」的表象，掩盖了真正的原因。**

### 🔴 阻断级不变量（Reviewer 提出，最高优先级）
> ## **过滤器只作用于「新入场候选」——已持有合约的退出管理不受任何影响**
>
> **已持仓合约的止盈、止损、平仓、到期处置、组合平仓管理，一律照常执行，与过滤器无关。**

**为什么这条是阻断级**：**META 那次「从 $300 跑到 $366」就是这么来的**——止损评估只遍历 campaign 列表，仓位一旦不在列表里就**失去止损管理**。**若实现者把「排除」写成「跳过该 symbol」（这是最自然的写法），已持仓仓位会同时失去退出管理。**

**实现硬要求**：**排除只作用于候选构建，绝不作用于持仓管理**——两者必须是**独立的代码路径**，且**排除动作不得触碰 campaign / 持仓状态**。

**对应验收**：构造「持仓合约落在排除名单里」→ **仍能正常止盈 / 止损 / 平仓**（见 §十一 验收 A0）。

## 四、候选质量判据（**硬排除** 与 **软评分** 分开）

### 🔴 硬排除（满足任一即不进候选池）
| 判据 | 阈值（默认） | 理由 |
| :--- | :--- | :--- |
| **已到期 / 当日到期** | **剩余到期 < 1 天** | 今晚 65 次被「合约已到期」挡下——**雷达在选 T-0 合约，是选品问题** |
| **报价停滞** | **`update_time` 停滞 > 180 秒** | 3 分钟无更新 = 低流动性；**这是流动性的代理指标**（若能取到成交量/持仓量，优先用更准的） |
| **盘口缺失** | bid ≤ 0 或 ask ≤ 0 | 无报价无法下单 |

### 🟠 软评分（**不排除，但降权排序**）
| 判据 | 阈值（默认） | 理由 |
| :--- | :--- | :--- |
| **价差** | 实盘 **≤ 5%** / 模拟 **≤ 10%** | **宽价差 = 高交易成本 + 差退出**；**超阈值不剔除，但排在候选末尾** |
| **成交量 / 持仓量** | 按可取数据定下限 | **流动性直接决定进出能力** |

> **为什么分两类**：**硬排除会造成「没有候选」**（今晚的教训）；**软评分保留「最差但可用」的选项**——**宽价差合约如果是最优候选，仍可交易，只是排在后面**。
> **硬排除只用于「数据不可信 / 无法交易」**（过期、无报价）。

### 🔴 硬要求：候选层与入场层阈值必须同源、且候选层 ≤ 入场层
**入场层盘口阈值是 20%**（`data_quality.py:33`）。**若候选层用另一套数字（如 50%），20%–50% 的合约会「入选后被拦」，产生不可解释的 BLOCK。**

**要求**：
1. **候选层价差阈值必须 ≤ 入场层阈值**（5%/10% ≤ 20% ✅）；
2. **两层阈值同源可配**——**同一份配置、同一个解析入口**，**不许多处写死**（沿用「一个概念一份实现」）；
3. **候选层硬排除的判据（到期/停滞/无报价）与入场层不重叠**——**候选层管「该不该选」，入场层管「数据可不可信」**。

### 关于价差阈值的说明
**实盘 ≤5% / 模拟 ≤10%**（采纳 Chief 建议）。**我原建议 8%/15%，现改为 5%/10%**，理由是：
- **价差是策略成本的主要构成**——5% 价差 ≈ 5% 往返成本，**对期权策略是显著摩擦**；
- **但紧阈值之所以安全，是因为它是「软降权」而非「硬排除」**——**5% 不会造成「无候选」**，只是排序靠后；
- **模拟区放宽到 10%**，**便于对照「严阈值 vs 松阈值」的成交差异**。

## 五、过滤点（**采纳 Architect 的落点判断**）

| 层 | 加什么 | 为什么 |
| :--- | :--- | :--- |
| **雷达扫描层**（`scan_market_layer`） | **只加正股级过滤**（正股无行情/停滞） | **雷达层只看得见正股、看不见合约盘口**（`volatility_scanner.py:200` 只对 underlying 取行情）——合约级判据在雷达层**拿不到数据**；硬放过去要在雷达层加一次合约行情调用，**那才是真正的性能坑** |
| **候选构建层**（`src/futu_quant/volatility_roll.py`：`rank_long_option_candidates` 之后、`rank_volatility_contracts` 之前） | **硬排除 + 软评分** | **已经在遍历合约候选**，加判据是同一趟循环；**在评分之前排除** → 不进排序、不进结构、不写 campaign |
| **入场门禁层**（`data_quality.py`） | **不动** | 900 秒硬上限是**最后一道防线**，已裁定不动 |

> **术语统一**：本 PRD 中的「**候选构建层**」= 设计文档中的同一层（`src/futu_quant/volatility_roll.py` 的 `:150`–`:161` 之间）。
> **雷达层（`scan_market_layer`）测不到合约级指标**（`update_time` 停滞、盘口缺失、DTE）——**合约是 `roll_campaign` 才选出来的**。**所以硬排除与 T-0 排除都在候选构建层判**。

> **软评分为什么不放入场层**（修正我原 PRD 的落点）：**入场层是「单笔」视角，没有「和其他候选比较」的上下文**——**「排末尾」这个语义只在候选层成立**。放入场层会**退化成硬排除**。

**性能要求（Architect 指出，属本设计唯一真风险点）**：
- **停滞判据需要 `update_time`，而候选构建层现在没有逐合约行情**——要判 180s 停滞**必须取一次行情**；
- **必须用 OpenD 批量 `snapshots`**（一次调用取全部候选合约），**严禁逐合约调用**；
- **验收**：断言候选构建层的行情调用**是批量的**（变异测试：改成逐合约调用 → 守卫转红）。

| 项 | 要求 |
| :--- | :--- |

## 七、可审计与可见性（**本次最重要的产品要求**）

### 1. 每个被排除的候选必须留痕
```
排除时间 / 标的 / 租户 / 策略 / 排除原因 / 当时的实测值（停滞秒数、价差、DTE）
```

**存储落点与四条硬约束**（Chief 裁定，Reviewer 提出）：
| 约束 | 说明 |
| :--- | :--- |
| **(a) 带 `tenant_id`** | **跨租户必须隔离**，否则排除记录混在一起 |
| **(b) 带实测值** | `age_seconds` / `spread_pct` / `volume` —— **否则「被排除」和「猜被排除」分不清** |
| **(c) 绝不写 `runtime_config` 或任何无前缀全局键** | **今天已踩过一次「测试写穿生产 `runtime_config`」**；而本过滤器**每轮 × 每标的都写**，**是最容易复发的形态** |
| **(d) 有 prune / 保留策略 + 表体积监控** | 高频写入，必须可控（Ops 加监控） |

**落点**：**新表 `candidate_exclusions`**（不强制塞 `audit_events`——高频 × 每轮每候选会把审计表冲垮，且需要按原因聚合）。

### 2. 排除原因必须可见
**监控页必须显示**：
- **候选池统计**：`候选 N 个 / 硬排除 M 个 / 软降权 K 个`
- **排除明细**：按原因分组，**可下钻到具体合约与实测值**

### 3. 为什么这条最重要
**今晚所有事故的共同点就是「静默」**：静默降级、静默过滤、静默熔断。
**一个新的静默过滤器，就是下一个事故。**——**用户必须能一眼看出「今天候选为什么这么少」。**

## 八、状态语义

| 状态 | 判据 | 展示 |
| :--- | :--- | :--- |
| 🟢 **候选充足** | 候选 ≥ 策略最小值 | 「候选 N 个」 |
| 🟠 **候选偏少** | 候选 < 策略最小值但 > 0 | 「候选偏少（N 个）· 硬排除 M · 软降权 K」 |
| 🔴 **无候选** | 候选 = 0 | 「无候选 · **硬排除 M 个**」+ **按原因分组的排除明细** |

**关键**：**「无候选」必须显示排除明细**——**否则用户会以为「没机会」，而实际是「被选品挡了」**（今晚就是这种误判）。

## 九、文案规范

| 场景 | 文案 |
| :--- | :--- |
| 硬排除 | `⛔ 硬排除 · US.XXX · 原因：报价停滞 1250 秒（阈值 180）` |
| 软降权 | `🟠 降权 · US.XXX · 价差 6.1%（阈值 5%）` |
| 无候选 | `🔴 无候选 · 硬排除 12 个 · 停滞 8 / 已到期 3 / 无报价 1` |

**禁止**：只写「无候选」而不写原因；只写「候选少」而不写排除数。

> **文案里的阈值必须与正文一致**（5%/10%）——**实现者会照文案写死数字**。

### 🔴 时区铁律：T-0 / DTE 必须按 **America/New_York** 计算
**CLAUDE.md 既有铁律**：**内部逻辑用 NY 时间，展示用中国时间**。

**T-0 排除、剩余到期天数、到期判定一律按 NY 计算**。**用北京时间会在 21:30（开盘）之后算错 DTE**——**NY 还在同一天，北京已是次日**，**会把未到期合约误判为已到期**。

**展示**：文案里给用户的「剩余 N 天」也**按 NY 口径**（与内部一致），**避免用户自己算出错觉**。

## 十一、验收（7 条，可演示）

1. **过期排除**：构造 T-0 合约 → **不进候选池** + 排除原因「已到期」。
2. **停滞排除**：构造 `update_time` 停滞 1250 秒 → **不进候选池** + 原因含实测秒数。
3. **价差不排除**：构造价差 9.2% 的合约 → **仍在候选池**，但**排在末尾**（软降权生效）。
4. **候选偏少可见**：构造只剩 1 个候选 → 页面显示「候选偏少 + 硬排除数 + 软降权数」。
5. **无候选可诊断**：构造全部被排除 → 页面显示**按原因分组的排除明细**（停滞 8 / 已到期 3 / 无报价 1）。
6. **按租户可配**：实盘阈值 180s、模拟阈值 600s → **模拟区候选更多**（证明租户隔离生效）。
7. **阈值缺失 fail-closed**：删掉阈值配置 → **记 ERROR + 拒绝该候选**（不是静默放行）。

### 🔴 必带验收（Chief 指定 + Reviewer 阻断项）
| # | 验收 | 判据 |
| :--- | :--- | :--- |
| **A0** | **退出管理不受过滤器影响**（🔴 **阻断级**） | 构造「持仓合约落在排除名单里」→ **仍能正常止盈 / 止损 / 平仓**；**排除动作不触碰 campaign / 持仓状态** |
| **A** | **低流动性合约不进候选池** | 构造停滞合约 → **不在候选池**，且 **`exclusion_reason` 可查可见** |
| **B** | **降级放行原因可见** | 构造 300–900s 报价 → **被 BLOCK**，且**原因可见**（不是静默） |
| **C** | **降级放行只对未排除候选生效** | 被候选池排除的合约，**不得走降级放行** |
| **D** | **变异测试** | **把过滤器关掉 → 守卫必须转红**（证明守卫不是空转） |

> **A0 是阻断级**：**不通过则不签字**——**META 那种「从 $300 跑到 $366」的失效模式会原样重演**。

## 十二、非目标（本期不做）
- 不做「低流动性降级通过」（**已裁定不做**——过期报价 + 自动下真金单 = 逆向选择）；
- 不做流动性预测 / 不做滑点模型；
- **不改 900 秒数据质量门禁**（**保持现状**，作为最后防线）。

## 十三、两个待用户拍板的口径（红区）

### 1. 降级放行上限 900s → 300s —— **同意，但必须带埋点，不得断言「无影响」**
**Reviewer 指出**：**两层在时间上分离**（扫描 → 建 campaign → 下一轮入场评估 → 选结构 → 下单），**候选在扫描时新鲜，不代表下单时新鲜**（中间可能隔一个周期）。**所以「影响几乎为零」是断言，不是实测。**

**裁定（Chief）**：
- **300s 先上线**；
- **必须带埋点**：记录「**候选入选 → 下单尝试**」的 `quote_age_at_submit`，**出 P50 / P95**；
- **一周后按数据复审**：**若 P95 逼近 300s，说明拦单过多 → 回退到 600s**；
- **不许写「无影响」这种断言**——**红区结论必须有依据**。

**方向性理由**（供参考，不作为依据）：**报价 15 分钟未动，即使双边盘口都在，限价也是基于失效价格**——**这正是逆向选择**。**300s 是「明显偏旧但不至于误伤短暂数据抖动」的线**。

### 2. 价差阈值实盘 ≤5% / 模拟 ≤10% —— **我同意，但强调它是「软降权」**
**已采纳 Chief 的建议**（我原建议 8%/15%）。**紧阈值之所以安全，是因为它是软评分而非硬排除**——**5% 不会造成「无候选」**，只是排序靠后。

**前提**：**软降权必须真正实现**——若实现成硬排除，**5% 会砍掉大量合约**，**反而回到「没有候选」的老问题**。**这条要在实现验收里钉死**。
