## 一、背景与问题

### 1. 现象：今日 0 单，但不是「没信号」
| 数据 | 值 |
| :--- | :--- |
| `volatility_scanner` | 884 条 HOLD |
| `volatility_long_gamma` | 721 条 HOLD + **344 条 BLOCKED** |
| `order_intents` | **0** |

**BLOCKED 构成**：
- **279 次「期权行情已过期」**——快照延迟 1116–1759 秒，超 900 秒阈值；
- **65 次「合约已于 2026-10-23 到期」**——⚠️ **经查清，这不是候选路径产生的**（来自 `gamma_debug.py:47` 的时区 bug，判的是**已有 campaign**），**不属本需求**，已单列 P0 缺陷。**本需求的 T-0 排除口径改为「按 NY 判定」**（见 §四）；
- 当日 `OPTION_MARKET_DATA_BLOCKED` 279 条、`OPTION_QUOTE_DEGRADED_ACCEPTED` 597 条。

### 2. 根因（Ops 实测确认，根因①）
两个被挡合约**已订阅、在链上、OpenD 报价正常**，但**报价自 10-23 12:20 / 12:52 起冻结**，三次读数（间隔 10 秒）完全不变；**同期正股每秒刷新**。

**判定：低流动性期权报价本身稀疏，30+ 分钟无更新是常态——不是订阅故障。**

### 3. 定性
**门禁在正常工作，不是故障。真正的问题是：雷达把「不该交易的合约」选进了候选池。**

**所以方向是「候选质量」，不是「放宽门禁」。**

## 三、产品目标
**让「不该交易的合约」在候选池阶段就被摘除**，而不是走到数据质量门禁才被 BLOCK——**后者制造「没单」的表象，掩盖了真正的原因。**

### 🔴 阻断级不变量（Reviewer 提出，最高优先级）
> ## **过滤器只作用于「新入场候选」——已持有合约的退出管理不受任何影响**
>
> **已持仓合约的止盈、止损、平仓、到期处置、组合平仓管理，一律照常执行，与过滤器无关。**

**为什么这条是阻断级**：**META 那次「从 $300 跑到 $366」就是这么来的**——止损评估只遍历 campaign 列表，仓位一旦不在列表里就**失去止损管理**。**若实现者把「排除」写成「跳过该 symbol」（这是最自然的写法），已持仓仓位会同时失去退出管理。**

**实现硬要求**：**排除只作用于候选构建，绝不作用于持仓管理**——两者必须是**独立的代码路径**，且**排除动作不得触碰 campaign / 持仓状态**。

**对应验收**：构造「持仓合约落在排除名单里」→ **仍能正常止盈 / 止损 / 平仓**（见 §十一 验收 A0）。

**结构性保障（Reviewer 核出，不需新代码）**：`roll_campaign` 在**候选为空时原样返回原 campaign + diagnostics**（`volatility_roll.py:172-175`）：
```python
if candidates.empty or "volatility_eligible" not in candidates:
    return _with_diagnostics(campaign, candidates, regime, "基础流动性筛选后没有可评分的新合约")
```
**所以「过滤到空 = 保留原 campaign = 退出管理照常」——A0 由结构保证。**

**A0 的落地因此只有两件**：
1. **一条回归测试**钉住「过滤到空 → 原 campaign 保留 → 退出管理照常」；
2. **明确禁止把过滤上移到遍历层**（`load_volatility_campaigns` / `reclaim_exit_only_orphans`）。

### 🔴 A0 的第二处落地：**既有代码里 A0 已被违反的实例**（Reviewer 核出）
**`run_gamma_strategy.py:448-454`**：
```python
issues = diagnose_campaign(campaign, executor.store.earnings_events())
hard_issues = hard_campaign_issues(campaign, issues)
if hard_issues:
    reason = "；".join(hard_issues)
    executor.store.decision(strategy_id, code, "BLOCKED", reason)
    return                      # ← 在任何动作之前 return
```
**`return` 发生在任何动作之前** —— **`hard_issues` 拦的不只是开仓，止盈 / 止损 / 平仓一起拦。**

**具体风险路径**：`diagnose_campaign` 对**任何** campaign 生效，而 `run_campaign` 被 `run_volatility_strategy.py` **共用**。campaign 来源有两条：雷达 `roll_campaign`（`min_dte ≥ 1`，通常不是 T-0），以及 **ADOPT**（`adopt_volatility_orphan_position`，**从券商已有持仓建 campaign——完全可能是当日到期合约**）。

**于是**：**持有 T-0 合约 → 北京 00:00（= ET 12:00）之后 → `date.today()` 已是次日 → 判「已到期」→ `return` → 该仓位的止盈/止损/平仓被完全冻结，直到 NY 16:00 它真的到期。** **冻结窗口正好是 ET 12:00–16:00 —— 最高 gamma 时段。**

> ⚠️ **时态说明（重要）**：**「T-0 冻结」是「修 TZ 前」的现象，修完即消失**——
> **当日到期时 `expiry == NY today`，不满足 `expiry < today`，不会被判已到期。**
> **所以修 TZ 之后，这条风险不再存在。**

**修法（与时区修复同批，两处一起改，否则只修一半）**：
1. **`gamma_debug.py:47` 的 `date.today()` → America/New_York**（含另外三处同类）；
2. **`hard_campaign_issues` 的 return 范围分家**：**「已到期」只应拦新开仓，不应拦平仓/止盈/止损**。判据形如 `if hard_issues and not is_exit_action: return`。
   **真实理由（不是 T-0）**：**其它 hard issue 同样会在任何动作前 return，把已持仓的止盈/止损/平仓一起冻结**——例如 **`财报时间未人工确认`**、**`期权代码无法识别`** 这类诊断命中时。**修掉时区只解决「误判到期」，不解决「诊断冻结退出」。**
   **这条保护的价值在于：以后新增任何诊断，都自动受它约束。**

### 时区修复清单（按「波动率实际经过的路径」重圈，已按用户优先级收窄）
**用户裁定**：**财报策略与币相关功能先不管**。**所以 `earnings_calendar.py` 那三处 `date.today()` 移出本批**（属财报路径）。

**本批保留的站点（4 处 + 1 处分家）**：
| 站点 | 风险 | 修法 |
| :--- | :--- | :--- |
| **`gamma_debug.py:47`** | **65 次假 BLOCK 的直接来源**；`diagnose_campaign` 对**波动率 campaign 同样生效** | `date.today()` → NY |
| **`option_ranking.py`** | **排序正确性**（不是「顺手改」）：`:72` 的 `dte` 直接喂给 `expiry_profit_probability(...)` → 决定 **probability / breakeven / confidence / 排序**；而 `volatility_roll.py:150` 的调用**没传 `as_of`** → 回落北京日期 → **DTE 最多差 1 天 → 概率与排序失真** | **在 `volatility_roll.py:150` 调用处传 `as_of=ny_today`，不改 `option_ranking.py:58` 的兜底默认值**（默认值影响所有调用方，影响面不可控） |
| **`run_volatility_strategy.py:141`** | 🔴 **平仓路径**用本地日期 → **NY 当日到期 combo 提前 ≤4h 被平仓**（与 65 次 BLOCK 同病、相反方向） | 改 NY |
| **`volatility_optimizer.py:932`** | 默认值本地日期（调用处已传 NY，**非必须**） | 兜底默认改 NY |

> **`option_ranking` 的守卫测试判据**（Reviewer 补充）：**不是「日期字符串正确」，而是「跨日期边界排序稳定」**——构造一个 DTE 在北京/纽约日期下差 1 天的合约 → 断言传入 `as_of=ny_today` 后其 **probability / rank 与预期一致**。**只测日期字符串会漏掉它的真实影响面。**

> **🔴 `hard_campaign_issues` 的修复不能因「财报策略不管了」而丢掉**（Reviewer 指出，我采纳）：
> `run_campaign` 定义在 `scripts/run_gamma_strategy.py`，**被 `scripts/run_volatility_strategy.py:284` 直接调用**——**波动率持仓走的是同一道「诊断出问题就 `return`、冻结全部动作（含平仓）」的门**。
> **放弃财报策略 ≠ 放弃这个修复**——**它保护的正是现在在跑的波动率策略。**
>
> **判据写死**：**凡参与到期判定 / 新鲜度判定 / 抓取窗口的日期，必须 `America/New_York`；仅用于展示与命名的时间戳保持本地。**（`feishu_reporter.py` / `health.py` / `migrate_*` / `ml_retrain_monthly.py` 那类**文件名与报告时间戳**用本地**无害且更符合用户阅读习惯**，**不做无收益改动**。）
3. **守卫测试两条**：
   - **mock 一个「非到期类」hard issue（如财报时间未确认）+ 持仓** → **退出动作不被阻断**；
   - **mock「北京 00:30 / NY 前一日」→ T-0 合约不得进 `hard_issues`**（TZ 修复的验证）。

> **测试口径说明**：**「真实已到期合约仍可平仓」不如「mock 非到期类 hard issue + 持仓 → 退出不被阻断」可测**——后者直接覆盖分家的真实理由。

## 四、候选质量判据（**硬排除** 与 **软评分** 分开）

### 🔴 硬排除（满足任一即不进候选池）
| 判据 | 阈值（默认） | 理由 |
| :--- | :--- | :--- |
| **已到期 / 当日到期** | **剩余到期 < 1 天** | **复用既有 `min_dte = max(1, ...)`（`volatility_roll.py:129-138`），按 NY 判定，不新造第二道**（见下） |
| **报价停滞** | **`update_time` 停滞 > 180 秒** | 3 分钟无更新 = 低流动性；**这是流动性的代理指标**（若能取到成交量/持仓量，优先用更准的）。**复用 `:145` 已有的批量 `quotes`，不新增行情调用** |
| **盘口缺失** | bid ≤ 0 或 ask ≤ 0 | 无报价无法下单 |

### ⚠️ 「T-0 排除」的口径修正（Chief + Reviewer 查清）
**今晚 65 次「合约已于 2026-10-23 到期」的 BLOCK，不是候选路径产生的**——来自 `gamma_debug.py:47` 的 `date.today()`（**本地=北京日期**），被 `run_gamma_strategy.py:449-454` 用来判**已有 campaign**，命中即 `return`。

**根因是时区 bug**：`gamma_debug.py:42-48` 用 `date.today()` 而非 NY 日期 → **10-23 到期的合约在北京 10-24 00:00（= ET 10-23 12:00）就被判「已到期」，比真实到期（ET 16:00）早 4 小时**。

**因此**：
1. **这 65 次的成因不是候选路径**——是 `gamma_debug.py:47` 的 TZ bug（既有缺陷），**新过滤器消不掉它**；
2. **但它的修复并入本批**——**因为 T-0 验收依赖「按 NY 判定」，而既有代码用北京日期，两者冲突**；
3. **本需求的 T-0 排除口径改为「按 NY 判定」**——**复用/收紧既有 `min_dte`，不是新增一道**；
4. **真实风险（⚠️ 修 TZ 前的现象）**：若持有当日到期合约，**北京 00:00 之后（ET 12:00–16:00，最高 gamma 时段）其止盈/止损/退出会被误判拦住**。**今晚恰好所有 campaign `qty=0`，只损失了 65 次假 BLOCK，未伤到仓位。**
   > **修 TZ 后这条风险消失**（当日到期 `expiry == NY today`，不满足 `expiry < today`）。**但 `hard_campaign_issues` 的 return 分家仍必须做**——理由是**其它 hard issue**（财报时间未确认 / 代码无法识别等）同样会冻结退出管理，见 §三。

**所以本批交付三处**：
| # | 内容 | 性质 |
| :--- | :--- | :--- |
| **①** | `roll_campaign` 候选层加流动性过滤 | **新需求** |
| **②** | `gamma_debug.py:47` 及同类 `date.today()` 统一改 NY + 守卫测试 | **既有 bug 修复**（65 次的直接来源） |
| **③** | **`hard_campaign_issues` 的 return 范围分家**——「已到期」只拦开仓，**不拦平仓/止盈/止损** | **既有缺陷**（A0 在既有代码里的违反实例，见 §三） |

### 🟠 软评分（**不排除，但降权排序**）
| 判据 | 阈值（默认） | 理由 |
| :--- | :--- | :--- |
| **价差** | 实盘 **≤ 5%** / 模拟 **≤ 10%** | **宽价差 = 高交易成本 + 差退出**；**超阈值不剔除，但排在候选末尾** |
| **成交量 / 持仓量** | 按可取数据定下限 | **流动性直接决定进出能力** |

> **为什么分两类**：**硬排除会造成「没有候选」**（今晚的教训）；**软评分保留「最差但可用」的选项**——**宽价差合约如果是最优候选，仍可交易，只是排在后面**。
> **硬排除只用于「数据不可信 / 无法交易」**（过期、无报价）。

### 🔴 硬要求：候选层与入场层阈值必须同源、且候选层 ≤ 入场层
**入场层盘口阈值是 20%**（`data_quality.py:33`）。**若候选层用另一套数字（如 50%），20%–50% 的合约会「入选后被拦」，产生不可解释的 BLOCK。**

**要求**：
1. **候选层价差阈值必须 ≤ 入场层阈值**（5%/10% ≤ 20% ✅）；
2. **两层阈值同源可配**——**同一份配置、同一个解析入口**，**不许多处写死**（沿用「一个概念一份实现」）；
3. **候选层硬排除的判据（到期/停滞/无报价）与入场层不重叠**——**候选层管「该不该选」，入场层管「数据可不可信」**。

### 🔴 阈值单源：**三项全接管**（Chief 裁定，定死口径）
**`screen_gamma_contracts` 的三处字面量 `500`（OI）/ `12`（价差硬筛）/ `10`（moneyness）全部由 `candidate_quality:{tenant}` 接管**，**默认值 = 现有字面量（行为不变）**。

**除这三项外，`screen_gamma_contracts` 其余逻辑本批不动**——**接管后不得再留字面量**。

**既有实现（Architect 核出）**：`earnings_gamma.py:16-34` **已有五道硬筛**（`bid>0` / `ask>0` / `OI≥500` / `spread≤12%` / `|moneyness|≤10` / 非停牌），**`:34` 排序是 `["atm_distance", "spread_pct"]`——价差只是 tiebreaker**。

**所以真正要新增的只有三样**：
| # | 新增 | 说明 |
| :--- | :--- | :--- |
| **①** | **报价停滞 >180s** | 判据用 `update_time`，**复用 `:145` 已有的批量 `quotes`** |
| **②** | **阈值租户化** | 即上面的「三项全接管」 |
| **③** | **`exclusion_reason` 留痕** | **现状：`screen_gamma_contracts` 把不达标的行直接丢掉，不留任何原因**——**这正是「静默」的确切位置** |

### 🔴 硬约束：**不能「只加不并」**
**若直接加新过滤 → 三道价差阈值并存**（既有 **12% 硬筛** + 新 **5% 软降权** + 入场层 **20%**）—— **正是「一个概念多份实现」**。

**因此**：
1. **既有 12% 硬筛由配置接管**（不新增第四道）；
2. **软降权必须进入主排序键**——现有排序是 `["atm_distance", "spread_pct"]`，**价差只是 tiebreaker**，**「排末尾」现在无法判定**；改为如 **`["soft_demoted", "atm_distance", "spread_pct"]`**，**否则 5% 阈值形同虚设**；
3. **接管后不得再留字面量**。

### 🔴 链式校验（fail-closed）—— 「单源可配」必须是「值自洽」
```
soft_spread_pct ≤ hard_spread_pct ≤ entry_max_spread_pct
```
**三者任一违反 → 拒绝解析 + 记 ERROR**。

**理由**（Reviewer 提出）：**若只校验软降权 ≤ 入场层，租户仍可把硬筛设成 25%**（> 入场层 20%）→ **候选层放行的合约被入场层拦下**，**「不可解释的 BLOCK」会从「配置错误」这条路上重新出现**。

### 关于价差阈值的说明
**实盘 ≤5% / 模拟 ≤10%**（采纳 Chief 建议）。**我原建议 8%/15%，现改为 5%/10%**，理由是：
- **价差是策略成本的主要构成**——5% 价差 ≈ 5% 往返成本，**对期权策略是显著摩擦**；
- **但紧阈值之所以安全，是因为它是「软降权」而非「硬排除」**——**5% 不会造成「无候选」**，只是排序靠后；
- **模拟区放宽到 10%**，**便于对照「严阈值 vs 松阈值」的成交差异**。

## 五、过滤点（**采纳 Architect 的落点判断**）

| 层 | 加什么 | 为什么 |
| :--- | :--- | :--- |
| **雷达扫描层**（`scan_market_layer`） | **只加正股级过滤**（正股无行情/停滞） | **雷达层只看得见正股、看不见合约盘口**（`volatility_scanner.py:200` 只对 underlying 取行情）——合约级判据在雷达层**拿不到数据**；硬放过去要在雷达层加一次合约行情调用，**那才是真正的性能坑** |
| **候选构建层**（`src/futu_quant/volatility_roll.py`：`rank_long_option_candidates` 之后、`rank_volatility_contracts` 之前） | **硬排除 + 软评分** | **已经在遍历合约候选**，加判据是同一趟循环；**在评分之前排除** → 不进排序、不进结构、不写 campaign |
| **入场门禁层**（`data_quality.py`） | **不动** | 900 秒硬上限是**最后一道防线**，已裁定不动 |

> **术语统一**：本 PRD 中的「**候选构建层**」= 设计文档中的同一层（`src/futu_quant/volatility_roll.py` 的 `:150`–`:161` 之间）。

**① 禁止把过滤器加到「遍历层」**

**② 复用已有批量行情，不新增调用**
**`volatility_roll.py:145` 已经有**：

**而插入点（`:150`–`:161` 之间）正好在 `quotes` 取到之后** —— **判停滞 / 盘口缺失直接用这份 `quotes` 即可，不需要新增任何行情调用**。

**③ T-0 排除已存在，复用而非新造**
**`volatility_roll.py:129-138` 已有**：

valid = expirations[(strike_time.date >= earliest) & (...)]

**`max(1, ...)` 保证 DTE ≥ 1，T-0 与已到期已被排除。**

**要求**：**复用/收紧这一处，不新写第二道**——**否则就是「一个概念两份实现」**。

**④ 租户入参必须显式**
`roll_campaign` **当前没有租户上下文**（`:93 roll_campaign(broker, campaign, store)`），而新配置是 `candidate_quality:{tenant}`、新表要 `tenant_id`。

### 🔴 待查清：65 次「合约已到期」BLOCK 的来源路径
PRD 说今晚 **65 次**被「合约已于 2026-10-23 到期」挡下。**若它不产生在 `roll_campaign` 里**（比如 ADOPT 建 `exit_only` campaign 那条路、或别的入口），**新过滤器加上去也消不掉这 65 次**。

**要求**：**实现前必须查清这条 BLOCK 的原因码从哪条路径产生**——**否则需求与实现会对不上**。**查清结果写进设计。**

> **软评分为什么不放入场层**（修正我原 PRD 的落点）：**入场层是「单笔」视角，没有「和其他候选比较」的上下文**——**「排末尾」这个语义只在候选层成立**。放入场层会**退化成硬排除**。

- **验收**：断言候选构建层的行情调用**是批量的**（变异测试：改成逐合约调用 → 守卫转红）。

## 七、可审计与可见性（**本次最重要的产品要求**）

### 1. 每个被排除的候选必须留痕
```
排除时间 / 标的 / 租户 / 策略 / 排除原因 / 当时的实测值（停滞秒数、价差、DTE）
```

**存储落点与四条硬约束**（Chief 裁定，Reviewer 提出）：
| 约束 | 说明 |
| :--- | :--- |
| **(a) 带 `tenant_id`** | **跨租户必须隔离**，否则排除记录混在一起 |
| **(b) 带实测值** | `age_seconds` / `spread_pct` / `volume` —— **否则「被排除」和「猜被排除」分不清** |
| **(c) 绝不写 `runtime_config` 或任何无前缀全局键** | **今天已踩过一次「测试写穿生产 `runtime_config`」**；而本过滤器**每轮 × 每标的都写**，**是最容易复发的形态** |
| **(d) 有 prune / 保留策略 + 表体积监控** | 高频写入，必须可控（Ops 加监控） |

**落点**：**新表 `candidate_exclusions`**（不强制塞 `audit_events`——高频 × 每轮每候选会把审计表冲垮，且需要按原因聚合）。

### 2. 排除原因必须可见
**监控页必须显示**：
- **候选池统计**：`候选 N 个 / 硬排除 M 个 / 软降权 K 个`
- **排除明细**：按原因分组，**可下钻到具体合约与实测值**

### 3. 为什么这条最重要
**今晚所有事故的共同点就是「静默」**：静默降级、静默过滤、静默熔断。
**一个新的静默过滤器，就是下一个事故。**——**用户必须能一眼看出「今天候选为什么这么少」。**

## 八、状态语义

| 状态 | 判据 | 展示 |
| :--- | :--- | :--- |
| 🟢 **候选充足** | 候选 ≥ 策略最小值 | 「候选 N 个」 |
| 🟠 **候选偏少** | 候选 < 策略最小值但 > 0 | 「候选偏少（N 个）· 硬排除 M · 软降权 K」 |
| 🔴 **无候选** | 候选 = 0 | 「无候选 · **硬排除 M 个**」+ **按原因分组的排除明细** |

**关键**：**「无候选」必须显示排除明细**——**否则用户会以为「没机会」，而实际是「被选品挡了」**（今晚就是这种误判）。

## 九、文案规范

| 场景 | 文案 |
| :--- | :--- |
| 硬排除 | `⛔ 硬排除 · US.XXX · 原因：报价停滞 1250 秒（阈值 180）` |
| 软降权 | `🟠 降权 · US.XXX · 价差 6.1%（阈值 5%）` |

> **文案里的阈值必须与正文一致**（5%/10%）——**实现者会照文案写死数字**。

### 🔴 时区铁律：T-0 / DTE 必须按 **America/New_York** 计算
**CLAUDE.md 既有铁律**：**内部逻辑用 NY 时间，展示用中国时间**。

**T-0 排除、剩余到期天数、到期判定一律按 NY 计算**。**用北京时间会在 21:30（开盘）之后算错 DTE**——**NY 还在同一天，北京已是次日**，**会把未到期合约误判为已到期**。

**展示**：文案里给用户的「剩余 N 天」也**按 NY 口径**（与内部一致），**避免用户自己算出错觉**。

## 十一、验收（**11 条**，与设计同数同序）

### 🔴 验收前置条件（阻断级）：**测试必须跑「本 worktree 的代码」**
**Architect 实测**：`.venv/Lib/site-packages/__editable__.futu_paper_quant-0.1.0.pth` 内容是 `E:\Thisyi\trade\src`——**项目以 editable 方式装进 venv，指向生产目录**。

**后果**：若 feature worktree 复用共享 venv，**pytest 跑本地 src（`pythonpath=["src"]` 前置），但 `python scripts/xxx.py` / 起服务会跑生产代码**。

**所以本 PRD 的全部验收（尤其 A0 / D 两条结构性测试）必须满足**：
1. **每个 worktree 独立 venv**（`uv sync` 各跑一次，editable 指向各自 src）——**代码与依赖都确定来自本 worktree，不靠纪律靠机制**；
2. **验收环境必须可证「跑的是哪份代码」**——**跑测试前断言解析到的 `futu_quant.__file__` 属于本 worktree**（守卫）；
3. **变异测试尤其要在正确环境里做**——**否则「把过滤器关掉 → 守卫转红」可能跑的是生产代码，给出假绿**。

**理由**：**今晚已经反复栽在「以为在改 A、其实在跑 B」**。**验收如果跑错代码，等于给自己发合格证。**

### 🔴 验收前置条件 ②：**worktree 的 `data/` 是空的**
**`data/` 是 gitignored** —— **feature worktree 没有 DB、没有配置**。

| 场景 | 影响 |
| :--- | :--- |
| **pytest 验收** | ✅ 无影响（用 tmp DB） |
| **手动冒烟测试** | ⚠️ **没有 DB / 配置，跑不起来** |

**要求**：**验收前必须 seed 一份最小数据集**（含候选合约、campaign、配置键），**并写明 seed 来源与内容**——**否则「验收通过」可能只是「没跑起来」。**

**seed 脚本自身必须带「不许写生产」守卫（阻断级）**：
- **断言 CWD 不是生产根**；
- **断言 DB 路径落在本 worktree 内**。

**理由**：`TradingStore()` 的默认路径是 **CWD 相对的 `data/trading.db`**——**从生产目录跑一次 seed，写的就是生产库**，**与今天那次事故是同一形态的高频操作**。

**seed 脚本随代码版本化**（`scripts/seed_test_env.py`，含 campaign / 候选 / 配置键）。

**基础（6 条）**
1. **过期排除**：构造 T-0 合约 → **不进候选池** + 原因「已到期」。**并验证是复用既有 `min_dte` 逻辑、非新造第二道**。
2. **停滞排除**：构造 `update_time` 停滞 1250 秒 → **不进候选池** + 原因含实测秒数。**并验证未新增行情调用**（复用 `:145` 的批量 `quotes`）。
   > 🔴 **验收 2 必须指定注入点（阻断级）**：`volatility_roll.py:145` 的 `broker.snapshots(...)` 是**实时行情**——**真实券商给不出一个「1250 秒前」的报价**。
   > **不指定注入点，这条验收就是「写出来但跑不了」的条目**——**而它在报告里和「假绿」长得一模一样**。
   > **要求二选一**：① **stub `broker.snapshots`** 返回带可控 `update_time` 的 DataFrame；② **seed 一张代码会读的表**。
3. **价差不排除**：构造价差 6.1% 的合约 → **仍在候选池**，但**排在末尾**（软降权生效）。
4. **候选可见性**：构造「候选偏少」与「全部被排除」两种场景 → 页面显示**「候选 N / 硬排除 M / 软降权 K」+ 按原因分组的排除明细**。
5. **按租户可配**：实盘阈值 180s、模拟阈值 600s → **模拟区候选更多**（证明租户隔离生效）。
6. **阈值缺失 fail-closed**：删掉阈值配置 → **记 ERROR + 拒绝该候选**（不是静默放行）。

**阻断与红区（5 条）**
| # | 验收 | 判据 |
| :--- | :--- | :--- |
| **A0** | **退出管理不受过滤器影响**（🔴 **阻断级**） | 构造「持仓合约落在排除名单里」→ **仍能正常止盈 / 止损 / 平仓**；**排除动作不触碰 campaign / 持仓状态**；**过滤器未被加到遍历层** |

| **D** | **变异测试** | **把过滤器关掉 → 守卫必须转红**（证明守卫不是空转） |

## 十三、两个待用户拍板的口径（红区）

### 1. 降级放行上限 900s → 300s —— **同意，但必须带埋点，不得断言「无影响」**
**Reviewer 指出**：**两层在时间上分离**（扫描 → 建 campaign → 下一轮入场评估 → 选结构 → 下单），**候选在扫描时新鲜，不代表下单时新鲜**（中间可能隔一个周期）。**所以「影响几乎为零」是断言，不是实测。**

**裁定（Chief）**：
- **300s 先上线**；
- **必须带埋点**：记录「**候选入选 → 下单尝试**」的 `quote_age_at_submit`，**出 P50 / P95**；
- **一周后按数据复审**：**若 P95 逼近 300s，说明拦单过多 → 回退到 600s**；
- **不许写「无影响」这种断言**——**红区结论必须有依据**。

**方向性理由**（供参考，不作为依据）：**报价 15 分钟未动，即使双边盘口都在，限价也是基于失效价格**——**这正是逆向选择**。**300s 是「明显偏旧但不至于误伤短暂数据抖动」的线**。

### 2. 价差阈值实盘 ≤5% / 模拟 ≤10% —— **我同意，但强调它是「软降权」**
**已采纳 Chief 的建议**（我原建议 8%/15%）。**紧阈值之所以安全，是因为它是软评分而非硬排除**——**5% 不会造成「无候选」**，只是排序靠后。

**前提**：**软降权必须真正实现**——若实现成硬排除，**5% 会砍掉大量合约**，**反而回到「没有候选」的老问题**。**这条要在实现验收里钉死**。
